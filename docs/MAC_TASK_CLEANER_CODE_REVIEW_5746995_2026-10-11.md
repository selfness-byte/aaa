## 1. 검토 범위와 증거 구분

## 2. 유지 가능한 개선 사항

CPU 계산기는 양의 변환비를 요구하고, full-width 곱셈·나눗셈으로 `floor(ticks * numer / denom)`를 구하며 표현 불가능한 몫을 거절한다. 합산 범위 초과, 실행 식별 불일치, 표본 세대 불일치를 거절하는 분기도 있다. [S1]

종료 상태 머신은 `allowedUID == 0`, 대상 UID 0, 타 사용자, 생존 정보 불일치, 신원 조회 실패, 보호 조회 실패를 종료 요청 전에 차단한다. 타임아웃의 RequestID 검사와 실행 종료 사실의 별도 저장도 유지된다. [S2]

작은 CPU 기대값 시험에는 `percentage > 0.0`과 `accuracy: 1e-27`이 실제로 들어 있다. 이 수정은 이번 커밋의 단위 러너에서 확인했다. [S8]

더미 앱은 `NSApplication`, `.regular`, 일반 종료 응답, 지연 응답을 사용하는 실제 AppKit 구성이다. 통합 시험은 NSWorkspace의 알림 센터를 사용하며, CPU 표본 구간에 의도적인 연산 부하를 준다는 코드와 로그가 있다. [S4], [S5]

## 3. 남은 수정 사항

### R1. 빠른 종료 시 관측 시각 계산이 비정상 종료할 수 있음 — 우선 수정

위치: [S4]의 Test 3, `tTermObserved` 초기화·대기 루프·Chronology 출력.

`tTermObserved`는 0으로 시작하고 대기 루프 본문에서만 설정된다. 요청 직후 또는 루프 진입 전에 `app.isTerminated`가 true이면 본문을 건너뛴다. 이후 최종 상태가 confirmed이면 `tTermObserved - tReq`를 UInt64로 계산한다. 미설정 값 0에서 양의 요청 시각을 빼면 정수 범위를 벗어난다.

동일한 뺄셈을 최소 프로그램으로 분리하여 `tTermObserved=0`, `tReq=343861508321500`을 입력했다. Swift 컴파일 반환값은 0, 실행은 Signal 4로 비정상 종료했으며 Python subprocess 반환값은 -4였다. 이는 산술 실패를 재현한 결과이지 macOS에서 빠른 종료 이벤트를 실제 발생시킨 결과는 아니다.

수정 방향: 미관측 시각은 Optional 등으로 표현하고, 즉시 종료 확인 경로에서도 관측 시각을 기록한다. 출력 직전 값의 존재와 시간 순서를 검사한다. 알림이 누락된 경우 `tracker.recordedTime - tReq`에도 같은 원칙을 적용한다. 실패를 기록하는 단언문이 이후 위험한 뺄셈까지 자동으로 중단시켜 주지는 않는다.

수용 시험: 루프 진입 전 종료, 루프 내부 종료, 알림 미수신의 각 경우에 기록이 정확하고 프로그램이 비정상 종료하지 않아야 한다. 미관측 값은 숫자 0으로 성공처럼 표시하지 않는다.

### R2. 시험 전용 대상·이벤트 연결이 선언한 제한보다 느슨함 — 대상 확대 전 수정

위치: [S4]의 `DummyAppTerminator`와 각 종료 알림 콜백.

종료 어댑터의 경로 검사는 `bundleURL?.lastPathComponent == "DummyTestTarget.app"`이다. 전체 예상 경로나 정규화된 실행 파일 경로를 비교하지 않으므로 같은 마지막 이름의 다른 위치까지 구분하는 검사는 아니다. 알림 콜백도 PID 일치만으로 보존한 ExecutionInstanceID에 종료 사실을 연결한다.

다만 현재 정상 경로는 지정한 앱 URL로 새 실행을 만들고, 보존한 NSRunningApplication 객체를 사용하며, 상태 머신은 커널 시작 시각과 UID를 재검사한다. 이 검토에서 실제 다른 앱이 종료됐거나 PID 재사용 공격이 성공했다는 주장은 하지 않는다. 지적은 어댑터·알림 연결 자체가 명세의 제한을 모두 강제하지 않는다는 점이다.

또한 `isAlreadyTerminated`는 요청 PID가 허용 PID와 다르면 true를 반환한다. 대상 불일치를 종료 사실로 바꾸는 계약이다. 이 반환값을 받는 상태 머신은 해당 실행을 observedTerminations에 기록할 수 있다. 대상 불일치는 종료 확인이 아니라 요청 차단 사유로 분리해야 한다. [S2], [S4]

수정 방향: 시험이 실행한 대상의 정규화된 전체 경로와 실행 기록을 보존·대조한다. 전역 알림은 보존한 앱 동등성·실행 연결 기록에 대응시키며, 종료 뒤 시작 시각을 새로 조회할 수 있다고 가정하지 않는다. 연결이 불명확하면 다른 실행에 귀속하지 않는다.

수용 시험: 경로 불일치·대상 불일치·오래된 실행 이벤트는 요청 호출 0회 또는 상태 불변이어야 한다. 이 반례 검사는 모의 입력으로 수행하고 실제 업무 앱을 시험 대상으로 추가하지 않는다.

### R3. CPU 수집기가 호출자가 넘긴 시작 시각을 그대로 신뢰함 — 실제 수집 정확성 보완

위치: [S3]의 `queryCPUTimeSample(for:generationID:)`.

수집기는 PID로 PROC_PIDTASKINFO를 읽지만 반환 CPUTimeSample의 시작 시각에는 실제 재조회 결과가 아니라 입력 instanceID의 값을 복사한다. PID의 실행이 바뀌었는데 호출자가 옛 식별자를 재사용하면 새 프로세스의 카운터에 옛 시작 시각을 붙일 수 있다. 두 표본의 식별자가 같다는 순수 계산기의 검사만으로 이 경우를 구분할 수 없다.

수정 방향: 초기 실행 발견과 기존 실행 검증을 구분하고, 실제 신원 조회를 CPU 수집 전후에 대조하여 불일치·조회 불가 표본을 거절한다. 별도 조회 사이의 경쟁 조건을 완전히 제거했다고 표현하지 않는다. generationID를 바꾸는 잠자기 연동 역시 주입값 검사와 별도다.

수용 시험: 옛 시작 시각을 가진 요청, 수집 중 실행 교체, 신원 조회 실패에서 CPU 표본을 정상값으로 반환하지 않아야 한다. OS 전체의 프로세스 목록을 임의로 종료할 필요는 없다.

### R4. 번들 준비·앱 준비 완료가 실패해도 후속 시험으로 진행 가능 — 재현성 보완

위치: [S4]의 `ensureAppBundle`, `launchDummyApp`.

번들 생성·기존 실행 파일 제거·복사·plist 기록에 `try?`를 사용하여 오류를 버린다. 이후에는 디렉터리 존재만 확인하고 verified라고 출력한다. 복사 실패로 기존 실행 파일이 남으면 검토한 소스와 다른 더미를 시험할 가능성을 배제하지 못한다.

앱 시작 대기도 제한 시간 뒤 `isFinishedLaunching`이 false인 채 반환할 수 있다. 저장된 Test 5 로그에도 false가 나타난다. 이는 정상 준비 완료를 확인한 시험과 시작 중 종료 시험을 구분하지 못하는 상태다. [S6]

수정 방향: 번들 준비는 오류를 전파하고 실행 파일·plist·예상 경로가 준비됐음을 확인한다. 정상 시나리오는 준비 완료 실패 시 중단하고, 시작 중 종료를 시험하려면 별도 이름과 기대 결과로 분리한다. 실패한 준비를 다른 위치의 앱으로 우회하지 않는다.

수용 시험: 복사·plist 실패, 준비 시간 초과에서는 정상 종료 시나리오를 통과로 처리하지 않는다. 이전 바이너리를 재사용했다면 그 사실과 버전을 명시해야 한다.

## 4. 저장된 CPU 값과 이벤트 시각 재계산

출처: [S6]. 아래는 해당 로그의 숫자를 다시 계산한 것이며 새 M1 측정값이 아니다.

- 사용자 틱 증가: 15,649,691 - 14,215,611 = 1,434,080
- 시스템 틱 증가: 9,434,009 - 9,425,507 = 8,502
- 합계: 1,434,080 + 8,502 = 1,442,582 ticks
- CPU 나노초: floor(1,442,582 * 125 / 3) = 60,107,583ns
- 단조 경과시간: 343,855,490,703,750 - 343,855,430,309,750 = 60,394,000ns
- CPU: 60,107,583 / 60,394,000 * 100 = 99.52575255820115%, 소수 둘째 자리 표시 99.53%

따라서 로그의 99.53%는 입력 표본과 일치한다. 시험용 연산 부하 구간이므로 대기 상태 CPU 1% 목표와 비교하지 않는다.

| 관측 구간 | 나노초 차이 / 1,000,000,000 | 초 |
| --- | --- | --- |
| 정상 요청 → 알림 | (343861629335708 - 343861508321500) / 1e9 | 0.121014208 |
| 정상 요청 → 종료 속성 관측 | (343861680186500 - 343861508321500) / 1e9 | 0.171865000 |
| 지연 요청 → 타임아웃 처리 | (343867447868208 - 343867143055083) / 1e9 | 0.304813125 |
| 지연 요청 → 알림 | (343868495489125 - 343867143055083) / 1e9 | 1.352434042 |

로그의 표기와 일치한다. 모든 실행에서 같은 알림 순서를 보장한다는 뜻은 아니다.

## 5. 다음 수정과 완료 기준

전체 설계를 다시 쓰기보다 R1–R4를 작은 수정으로 반영하고 관련 회귀 시험을 추가한다. 수정 커밋에 기존 1~2단계와 더미 전용 3단계 결과, 명령, 실행 환경, 실제 종료 코드를 연결해 보존한다. 정상 경로의 성공과 오류 경로 방어를 분리해 판정한다.

실제 사용자 앱 종료, 무손실 저장, 모든 PID 경쟁 조건 제거, 장시간 누적 없음, M1 대기 CPU 1%·physical footprint 100MB 달성은 이번 검토에서 인증하지 않는다. 대기 성능과 실사용 대상 확대는 별도 단계다.
